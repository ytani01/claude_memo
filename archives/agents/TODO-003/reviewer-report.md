## 1.【要修正／要判断】画面が 16:9 ちょうどのタッチ端末では、直ってもなお抜けられない

**箇所**: `claude_memo.html:236-252`（新しい `@media` ブロック全体）と、
`claude_memo.html:117-128`（`#viewport-stage.is-fullscreen` の
`max-width: calc(100vh * (16 / 9))` / `max-height: calc(100vw * (9 / 16))`）

**何が起きるか**: レターボックスが画面いっぱいになる比率
（＝画面が 16:9 ちょうど）のとき、暗幕の露出面積が 0 になる。暗幕は出て
いるがラッパーの下に完全に隠れるので、`e.target === stage` になる座標が
どこにも無く、タップで抜けられない。ボタンは箱の裏、物理キーボードも無い
ので、TODO-003 が直そうとしたのと同じ「再読み込みしか出口が無い」状態が
残る。

**根拠（実測、`rv5.py`）**: タッチあり・幅 768 以上で、フルスクリーンに
入れてから画面の上下左右の端（各辺の中点、端から 2px）を実クリックした
結果。`band_x` / `band_y` はレターボックスの左／上の余白。

| 画面 | 余白 (x, y) | 4 辺のどこかで抜けられたか |
|---|---|---|
| 1280x720 | 0, 0 | **抜けられない** |
| 1024x576 | 0, 0 | **抜けられない** |
| 960x540  | 0, 0 | **抜けられない** |
| 800x450  | 0, 0 | **抜けられない** |
| 1024x600 | 0, 12 | 上端で抜けられた（帯は 12px しかない） |
| 844x390  | 75, 0 | 左端で抜けられた |

横持ちで 16:9 ちょうどになるタッチ端末（1920x1080 や 1280x720 の
Android タブレット、16:9 のタッチディスプレイ）が該当する。
利用者が挙げた 844x390 のような 19.5:9 以上の今どきのスマホは 75px の
帯が出るので問題ない。

**直す場合の案**（どれを採るかは管理者・利用者の判断）:

1. 何もしない。対象端末が 16:9 ちょうどのタッチ画面に限られるなら、
   TODO.md の「対応しない」に理由付きで残す（**最小の対応**）
2. タッチ画面のときだけレターボックスを少し小さくして、帯を必ず作る。
   例: `(pointer: coarse)` のブロックで
   `#viewport-stage.is-fullscreen { max-width: calc(100vh * (16/9) - 88px); }`
   のように余白を確保する。ついでに 1024x600 の 12px という
   「狭すぎて狙えない帯」（タップ目標の目安は 44〜48px）も解消する
3. タッチ画面のフルスクリーン中だけ、ラッパーの中に閉じるボタンを出す

なお 1024x600 のように「帯はあるが 12px」という端末は、上の表のとおり
仕組みとしては抜けられるが、実機の指では狙えない可能性が高い。
案 1 を採るなら、この点も併せて許容すると決めておくのがよい。

## 2.【検討】`CLAUDE.md` と CSS コメントの「レターボックスが横にずれる」の説明が、実測と食い違う

**箇所**: `CLAUDE.md:58-62`、`claude_memo.html:234-235`
（「PC で裏をスクロール禁止にするとスクロールバーが消え、100vw 基準の
レターボックスが横にずれる」）

**何が起きるか**: 今回の差分はマウスの PC の挙動を変えていないので、
**動作上の実害は無い**。ただし、この文は今後この箇所を触るときの根拠に
なる。実測すると、書かれているのと逆の効果の方が大きい。

**根拠（実測、`rv2.py`。実ウィンドウ、スクロールバー幅 6px）**:

- 800x600（レターボックスの幅が `max-width` で切られない比率）:
  - fs-lock **無し**（現状の PC）: `clientWidth` 794 に対して
    レターボックスは `[0, 800]`、`margin-right: -6px`。
    つまり**スクロールバーの下に 6px 食い込んでいる**
  - fs-lock **有り**: スクロールバーが消えて `clientWidth` 1000、
    レターボックスは `[0, 800]`、`margin` は 0 で食い込みが消える
- 1000x600（`max-width` で切られる比率）:
  - fs-lock 無し: レターボックス `[41, 953]`
  - fs-lock 有り: `[44, 956]`。**スクロールバー幅の半分（3px）だけ右へ動く**

まとめると、fs-lock で起きるのは「スクロールバー幅の半分のずれ」と
「裏のページ全体がスクロールバー幅ぶん右へ動くこと」で、比率によっては
むしろ fs-lock の方が正しい位置になる。Windows など 15px のスクロールバー
なら 7.5px 程度のずれになる計算。

**直す場合の案**: `CLAUDE.md:58-62` と CSS コメントを
「裏のページとレターボックスがスクロールバー幅ぶん（レターボックスは
その半分）横に動く」程度の表現に直す。あるいは、この記述の出所は
TODO-001 なので、**当時の観察は裏のページのずれを見ていた可能性**があり、
ずれの正体を書き直すだけでも次に触る人の判断が変わる。

## 3.【検討】古典的なスクロールバーを持つタッチ PC では、フルスクリーン開始時に裏が数 px 動く

**箇所**: `claude_memo.html:236`（`screen and (pointer: coarse)` を

**何が起きるか**: `(pointer: coarse)` を返す幅広の端末（Chrome OS の

スクロールバー幅ぶん、レターボックスがその半分だけ横に動く（項 2 の実測）。

**未確認**: 実機の Windows タブレット／Chrome OS では確認していない。
Playwright の `has_touch=True` は `(pointer: coarse)` を true にするが、
スクロールバーの実装までは実機と同じではない。

## 4.【問題なし・確認結果】`(pointer: coarse)` の選択は妥当

`(any-pointer: coarse)` は、**マウスを使っているタッチ対応ノート PC にも
当たってしまう**（Playwright の `has_touch=True` 条件で
`any-pointer: coarse` が true になることを実測）。`pointer` は主たる
ポインタだけを見るので、マウス主体の PC は従来どおり除外される。
`(hover: none)` でもほぼ同じ結果になるが、「触る画面か」を表すのは
`pointer` の方が素直で、既存の説明文とも合う。**今の選択でよい。**

メディアクエリのリストの順序も良い。`pointer` を解釈できない古い
ブラウザでは 2 番目のクエリだけが無効になり、
`max-width: 767.98px` の側は生き残る（リスト内の無効なクエリは
その 1 つだけが捨てられる）ので、縦持ちスマホの挙動は守られる。
