## 要修正

### 1. 幅 620〜712px 前後・タッチ画面で、変更後も枠が画面の下へはみ出す
（実機でも起きる。iPhone SE の横持ち 667x375 で実測 +16px）

`claude_memo.html:214-215`

```css
max-width: calc((100vh - 89px) * (16 / 9));
max-width: calc((100dvh - 89px) * (16 / 9));
```

89px（ヘッダー 65px + 本文上余白 24px）は**幅によって変わるヘッダーの高さを
定数化したもの**だが、ヘッダー（`claude_memo.html:310`, `py-2 sm:py-3` で
`sm`=640px を境に高さが変わる）は、`sm:` が効いて右上のバッジや音声エンジンの
ラベルが表示され始める幅帯（実測で概ね 640〜712px）で**折り返して 89〜105px
まで伸びる**。ここでは本文の上余白も `md:p-6`（768px 境）が効かず 16px のまま
なので、実際に引くべき値は最大 121px（105+16）になる。CSS は常に 89 しか
引かないため、この帯では枠が計算どおりに縮まらず画面の下へはみ出す。

実測（`height: 420` 固定、タッチ画面）:

| 幅 | ヘッダー実測高さ | frame top | frame bottom | はみ出し |
|----|----------------|-----------|---------------|---------|
| 640px | 105px | 121 | 452 | **+32px** |
| 660〜710px | 89px | 105 | 436 | **+16px** |
| 720〜767px | 65px | 81 | 412 | -8px（安全側、後述） |
| 768px 以上 | 65px | 89 | md:p-6 で 24px → 89 | 0（一致） |

実機に近い例（iPhone SE 横持ち, 667x375, タッチ）:

- 変更前（`git show HEAD:claude_memo.html`）: frame bottom 462 / innerHeight 375 →
  **+87px** はみ出し
- 変更後: frame bottom 391 / innerHeight 375 → **+16px** はみ出し

変更前よりは改善しているが、TODO-011 の目的（「横持ちの通常表示でスライド
全体が見える」）はこの実機サイズでは達成できていない。

**どう直すか（案）**: 89 という定数はヘッダーの Tailwind クラス
（`py-2 sm:py-3`）に依存する値で、CSS 側に固定で書くと折り返しの帯で必ず
ずれる。既存の `--vp-scale`（`ResizeObserver` で実際の幅から出す）と同じ
考え方で、ヘッダー＋本文上余白の**実際の高さ**を JS で測って CSS 変数に
入れる方が、この種のずれが起きない。CSS だけで済ませるなら、少なくとも
640〜767px の帯（`sm:` が効いてヘッダーが折り返す帯）を含めて実測し直し、
その帯でも安全側（大きめに引く）になる定数を選ぶ必要がある。

### 2. コメントの「65px」「24px」は範囲によって成立しない値

`claude_memo.html:208-209`

```
画面の高さからヘッダー（65px）と本文の上余白（24px）を引いた分を高さの上限とし
```

上の 1. のとおり、この 2 つの値は幅 720px 以上でしか成立しない
（640〜712px 帯ではヘッダーが 89〜105px になる）。「実測」の書き方だが、
実際には 1 点の測定（おそらく 844x390 か PC 幅）をそのまま全域の定数として
書いている。1. を直すのに合わせて、このコメントも「どの幅で成立するか」を
明示するか、実測ベースの表現に直す方がよい。

## 検討

### 3. 定数の由来がどこにも書かれておらず、対で保守する仕組みが無い

89px はヘッダーの `py-2 sm:py-3`（`claude_memo.html:310`）と本文の
`p-4 md:p-6`（`claude_memo.html:336`）から来ているが、その対応関係は
コード上どこにも紐付いていない（コメントに数字が書かれているだけ）。
将来ヘッダーの padding やバッジの表示条件を変えると、この 89 も直さないと
ずれるが、それに気付く仕組みが無い。1. の修正で JS 実測に切り替えれば
自然に解消する。CSS のままにするなら、`CLAUDE.md` の「触るときの注意」に
「ヘッダーの高さを変えたらここも直す」という注記を足す価値がある
（既存の「ボーダーの太さを変えたら一緒に直す」と同種の書き方）。

### 4. 実測結果が報告として残っていない

`archives/agents/TODO-011/measure.js.txt` はスクリプトのみで、実行結果が
保存されていない。この 1 件自体は verifier の担当範囲だが、reviewer 目線でも
「動くはず」で止まっている状態だったので、上の 1. の実測は今回このレビューで
初めて数値化した。verifier に依頼する際は、640〜767px 帯（タッチ）と実機に近い
サイズ（667x375 など）を測る条件に加えるとよい。

## 問題なし（確認した点）

- `#viewport-stage.is-fullscreen > #viewport-frame { max-width: none }` は、
  TODO-001 で `:has()` を避けて JS（`setFullscreen()`）がクラスを付け外す
  形にした経緯と整合している。既存の `#viewport-stage.is-fullscreen >
  #subtitle-banner`（`claude_memo.html:235`）と同じパターンで、`:has()` は
  使っていない
- `margin-inline: auto` は、`max-width` で幅が縮んだときに枠を中央に置くために
  必要（無いと flex の stretch で左端に寄る）。844x390・タッチで実測した
  `frame.left = 154` は、中央寄せが効いた値と一致
- `vh` の行を先に置き `dvh` で上書きする順序は、TODO-004 の前例と同じ
- フルスクリーン中（横持ち・縦持ち）と PC（1280x800）、縦持ちの通常表示
  （390x844）は実測どおり無変化（縦持ちでは `max-width` が画面の幅より広く
  効かない）。TODO.md のチェックリスト 2 項目目「縦持ち・フルスクリーン・PC
  の見え方が変わらないことを確かめる」はこの範囲では満たしている
- コメントの書き方（TODO 番号の参照形式、「なぜ」の説明）は既存のファイルの
  スタイルと揃っている。造語は見当たらない
- 差分の範囲は依頼どおりで、無関係な変更は混ざっていない
