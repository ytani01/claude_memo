## きっかけ

TODO-001 のレビューで見つかった、幅 768px 以上に残る穴
（`archives/agents/TODO-001/reviewer-report-3.md` の検討 3・4）。
TODO-001 は縦画面の項目なので、こちらに分けた。

スマホを横にすると 844x390 のように幅が 768 以上になり、PC 扱いになる。
暗幕（`#viewport-stage.is-fullscreen::before`）も `body.fs-lock` も
`@media (max-width: 767.98px)` の中にあって効かない。フルスクリーンから
抜ける手段は 3 つ（ボタン・Esc・暗幕のタップ）あるが、ボタンは箱の裏で
押せず、物理キーボードも無く、暗幕も出ないので、再読み込みしか出口が
無かった。縦に戻せば抜けられる。

## やったこと

`claude_memo.html` の `<style>` で、`body.fs-lock` と
`#viewport-stage.is-fullscreen::before` の 2 ルールを
`@media screen and (max-width: 767.98px)` のブロックから出し、
`@media screen and (max-width: 767.98px), screen and (pointer: coarse)` の
新しいブロックへ移した。タッチ画面なら幅によらず縦持ちと同じ出口が出る。

- `--vp-scale` による縮小は 767.98px 未満のままで、変えていない
- JS は幅で分岐していない（`setFullscreen` はクラスを常に付け外しし、
  暗幕タップのハンドラは `e.target === stage` だけを見る）ので、変更なし。
  コメントの「768px 未満の暗幕」という表現だけ直した
- `CLAUDE.md` の `body.fs-lock` の節を条件に合わせて書き直した

レビューの指摘で、同じ節の「PC で fs-lock を掛けるとレターボックスが
横にずれる」という記述が実測と食い違っていることが分かったので、
併せて直した。実際に起きるのは「裏のページがスクロールバー幅ぶん、
レターボックスがその半分だけ動く」で、比率によっては fs-lock を掛けた方が
正しい位置になる（TODO-001 当時の観察は裏のページのずれを見ていたと思われる）。

## 確かめたこと

verifier が Playwright（システムの chromium）で実測した
（[verifier-report.md](../agents/TODO-003/verifier-report.md)）。

- 844x390（タッチ）/ 390x844（タッチ）/ 1280x800（マウス）の 3 条件で、
  暗幕の有無・`body` の overflow・スクロールバーの有無を `git stash` で
  変更前と比べた。変わったのは狙った 2 点だけ
- 844x390 で、変更前は `elementFromPoint` が背景の要素を返してタップしても
  抜けられず、変更後はラッパーを返してタップで抜けられる、という反転を
  実座標のクリックで確認した。390x844 は変更前後で同じ
- 字幕が画面外へはみ出しても、裏のページに余分なスクロールバーは出ない

reviewer は HEAD との computed style の全プロパティ比較で、詳細度・記述順の
回帰が無いことと、`(pointer: coarse)` の選択が妥当であることを確かめた
（[reviewer-report.md](../agents/TODO-003/reviewer-report.md)）。

## 対応しないと決めたこと

- **フルスクリーン中に字幕が画面外へ出て切られる件**（2026-09-18）。
  横持ちや低い画面では 16:9 の箱の下に余白が無く、`top: 100%` で置いた
  字幕がはみ出す。字幕は見えなくてよいと利用者が判断した。裏のページに
  スクロールバーを出していないことは上のとおり確認した
- **横持ちでは枠の高さが画面の高さを超え、通常時に縦スクロールが要る件**
  （2026-09-18）。変更前から同じ挙動で、フルスクリーンにすれば解決する
- **画面が 16:9 ちょうどのタッチ端末で、直してもなお抜けられない件**
  （2026-09-18 にレビューで見つかり、同日に利用者が決めた）。暗幕の帯は
  画面の比率で決まるので、1280x720 や 960x540 では帯が 0px になり、
  `e.target === stage` になる座標がどこにも無い。該当するのは 16:9 の
  タッチ画面（Android タブレットなど）で、844x390 のような今どきのスマホは
  75px の帯が出る。1024x600 の帯が 12px しかなく指では狙いにくい点も、
  併せて許容する

## 分担の振り返り

- **verifier は「指示どおりか」を実測で埋めた。** Playwright を自分で見つけ、
  変更前との比較まで組んだ。ただし最初の報告では暗幕タップを合成イベントで
  しか確かめておらず、実座標での確認は追加で頼んで初めて出てきた。
  依頼文に「実際の座標で叩くこと」まで書いておけば 1 往復減った
- **reviewer だけが、直した先に残る詰みを見つけた。** 16:9 ちょうどの端末で
  帯が 0px になる件も、CLAUDE.md の記述が実測と食い違う件も、
  「指示どおりか」を見る verifier の射程には入らない。挙動の条件が変わる
  項目にレビューを入れる決まりが、そのまま効いた
- **見込みと食い違ったのは implementer を立てなかった点。** 着手して
  コードを読んだら、変更が CSS 2 ルールの移動に収まると分かった。
  依頼文を書いて報告を読む往復の方が、差分そのものより大きくなる規模だった
- **次に同じ規模（1 ファイル・数行・条件式が変わる）なら、同じ組み方でよい。**
  main が実装し、verifier と reviewer を並列で 1 回ずつ。減らす余地は
  reviewer の 50%（$1.9）だが、ここを削ると今回の 2 件が出てこない。
  削るなら verifier の依頼文を具体的にして往復を減らす方
