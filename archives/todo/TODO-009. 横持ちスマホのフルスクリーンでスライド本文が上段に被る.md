## きっかけ

横持ちのスマホでフルスクリーン（最大化）にすると、スライドの表題が枠内上段
（`#slide-category` と `SLIDE nn / 17` の行）に一部重なった。

横持ちのスマホは幅が 768 以上なので PC 側の経路に入り、`--vp-scale` での縮小が
効かない。一方フルスクリーンの箱はレターボックスなので実寸が 960x540 より小さく
（844x390 の端末で約 693x390）、本文の `clamp(1.4rem, 3.2cqw, 2.5rem)` などの
下限 px が効いて文字が縮まなくなる。本文が入り切らず、`#slide-canvas` の
`my-auto` が上下へ均等にはみ出すため、上段に重なっていた。

## やったこと

`claude_memo.html` の縮小経路のメディアクエリを広げた。

```css
/* 変更前 */ @media screen and (max-width: 767.98px) {
/* 変更後 */ @media screen and (max-width: 767.98px), screen and (pointer: coarse) {
```

これで横持ちのスマホも 960x540 を `--vp-scale` で縮める経路に入り、PC と同じ
組み方のまま丸ごと縮む。`clamp()` の下限 px は 960px 基準で解決されるので効かない。
条件は暗幕・`fs-lock` のメディアクエリ（TODO-003 で足したもの）と同じ文字列に揃えた。

`clamp()` の下限を個別に下げる案と、`#slide-canvas` の `my-auto` をやめて
下を切る案も出したが、利用者が縮小経路に寄せる方針を選んだ。

**フルスクリーン中に限らず、タッチ画面なら通常表示でも縮小経路に入る。**
レビューで「タブレットやタッチ対応 PC（1366px 相当）でも、字幕が枠に重ならず
下へ流れ、枠内の固定 px のクロームが `--vp-scale` 分小さくなる」と指摘されたが、
利用者と相談してこのままにした。フルスクリーンだけに絞ると、同じルールを
`#viewport-stage.is-fullscreen` 付きでもう一組書くことになり、CSS が 40 行ほど
増える。タッチ画面では常に同じ描き方になるほうが単純で、実害も見た目の違いだけ。
TODO-003 では縮小経路を 767.98px 未満のままにしたので、そことは違う判断になる。

`CLAUDE.md` の「触るときの注意」も、縮小経路の条件がタッチ画面を含むように直した。

## 確かめたこと

verifier が Playwright（chromium）で `file://` を開き、全 17 スライドの
`getBoundingClientRect()` を実測した。報告と生データは
`archives/agents/TODO-009/` にある。

| 条件 | 上段 bottom と canvas top の差 | 判定 |
|------|------------------------------|------|
| 844x390・タッチ・フルスクリーン | +2.89 〜 +6.15px | 重なり無し |
| 844x390・タッチ・通常表示 | +5.23 〜 +5.96px | 重なり無し |
| 1280x800・タッチ無し（PC） | +5.94 〜 +6.73px | 縮小経路に入らず、回帰無し |

フルスクリーン中に暗幕をタップして抜けられること（TODO-003 の挙動）も
844x390 で壊れていないことを確かめた。

## 残ること

844x390 では、本文の下端が `#player-viewport` の padding 内側を 1.6〜7px
食い込んでいる（フルスクリーンで 3.7〜6.9px、通常表示で 1.6〜2.4px）。枠の
見た目の外周までは 18px 以上余裕があり、操作要素とも重ならないので、
そのままにした。PC（1280x800）では逆に 1.9〜2.7px の余裕がある。

## 分担の振り返り

- **verifier** は 3 条件 × 17 スライドを実測し、上段との重なりが解消したことと
  PC の回帰が無いことを数値で示した。あわせて、当初の症状には無かった
  「下側の padding への食い込み」を見つけた
- **reviewer** は、広げたメディアクエリがフルスクリーンにスコープされておらず、
  通常表示のタッチ画面（1366px、1024px）にも及ぶことを実測付きで指摘した。
  これは main が変更時に意識していなかった副作用で、TODO-003 の前例
  （縮小経路は 768px 未満のまま）との食い違いも突き止めている。
  `CLAUDE.md` の説明が幅の条件しか書いていない点も拾った
- 見込みとの食い違いは無い。差分 1 行でも、確認とレビューを分けた効果が
  そのまま出た（実測は verifier、分岐の意味の変化は reviewer が拾い、
  どちらも main 単独では出てこなかった）
- 次に同じ規模（CSS の条件を 1 行変える類い）をやるなら、同じ組み方でよい。
  ただし reviewer は 21 メッセージで料金の 27% を使っており、差分が小さい
  項目では「差分と、その条件が使われている全ルール」に読む範囲を絞って
  依頼すれば減らせる。verifier への依頼で測る条件を 3 つに限定したのは効いた
  （17 スライド全件でも 24 メッセージで収まった）
