## きっかけ

スマホでは前後ボタンが小さくしか出ない（枠の外のクロームは幅 768px 未満で
`text-xs` が選ばれ、さらに `--vp-scale` 倍される）。横スワイプでも
スライドを送れるようにする。

同じ `#player-viewport` にはタップで再生／一時停止を切り替えるハンドラ
（TODO-005）が載っているので、スワイプをそちらに通さないことが要点だった。

## やったこと

`claude_memo.html` の `#player-viewport` に `touchstart` / `touchend` を足した
（タップのハンドラの直前）。

- 切り替えは `next-btn` / `prev-btn` の `click()` に投げる。`renderSlide()` を
  直に呼ばないので、ボタンを押したときと挙動が同じになる
- 判定は**距離と方向だけ**。横に 50px 以上動き、横の移動量が縦より大きいとき
  だけスワイプと見なす。**速さは見ない**
- `preventDefault` を呼ばないので `{ passive: true }` のまま。縦スクロールを
  妨げない
- スワイプの後に飛んでくる `click` は `swiped` フラグで止める。フラグは次の
  `touchstart` で必ず落とすので、`click` が来なくても次のタップに持ち越さない
- 2 本目の指が触れたときは `touchStarted` を下ろし、ピンチをスワイプと
  誤認しない

**時間のしきい値は、いったん入れてから外した。** 当初は 600ms 以内という
条件も付けていたが、レビューで「距離を満たしても時間切れなら `swiped` が
立たず、直後の `click` が再生／一時停止に化ける」と指摘された。時間の条件を
外す（ゆっくり滑らせても送る）方を利用者が選んだ。条件が 1 つ減り、
`touchStartAt`（時刻）も `touchStarted`（真偽値）で済むようになった。

## 確かめたこと

- **verifier**: Playwright（chromium、`has_touch` / `is_mobile`、390x844）で
  合成タッチイベントを発火させ、10 パターンを実測。左右スワイプでの切り替え、
  スワイプ後の `click` 抑止、縦スワイプ・短い移動での非反応、単純タップでの
  再生／一時停止、フラグの持ち越し無し、先頭・末尾での安全動作、
  ゆっくりしたスワイプ（1000ms・80px）での切り替え。すべて期待どおり
  （PAGE ERROR 無し）。報告は `archives/agents/TODO-010/verifier-report.md`
- **reviewer**: 要修正 0 件、検討 3 件。上に書いた時間のしきい値の件が検討 1。
  検討 2（`#slide-canvas` 内の `overflow-x-auto` との干渉）は実測で
  `scrollWidth === clientWidth` を確認し、現状のコンテンツでは横スクロールが
  そもそも発生しないため実害無し。検討 3（`touchcancel` 未 listen）も
  次の `touchstart` で必ず上書きされるため抜けは無い。
  報告は `archives/agents/TODO-010/reviewer-report.md`
- **実機**: 利用者がスマホで確認

`clientX` を使う点は reviewer が実測で確かめた。`#player-viewport` は
`transform: scale()` で縮むがレイアウトは 960x540 のままで、`clientX` は
transform 適用後の実画面座標で来る。したがって 50px は「指が実際に動いた
画面上の距離」として、`--vp-scale` がいくつでも同じ意味になる。

## 分担の振り返り

- **verifier** は自動化の手段（Playwright）を自分で見つけ、10 パターンを
  実測した。静的な読みで済ませなかった。**reviewer** は時間のしきい値の
  穴（距離を満たしても時間切れで `click` に落ちる）を見つけた。これは
  verifier のテストでは捕まらない——テストは通っていて、動きが「良くない」
  だけだったため。「動くか」と「良いか」を分けた効果が出た
- 見込み（verifier + reviewer）と実施は食い違わなかった。挙動が変わり、
  分岐が増える項目なので reviewer を入れる判断は最初から付いていた
- **次に同じ規模（1 ファイル・1 ハンク・イベント処理の追加）なら、同じ
  2 人でよい。** ただし main が 61%（$1.7）を占めた。実装そのものは
  40 行ほどで、main の消費の多くは 2 人の起動と報告の読み込み、それに
  実機確認の待ちに費やされている。**報告は最初から「要修正の有無 + 検討の
  件数」だけ返させ、本文は必要なときだけ読む**ようにすれば、もう少し減る
