## きっかけ

PC ブラウザでは 16:9 を前提に見やすく調整済みだったが、スマホの縦画面が
未調整だった。当時は `@media screen and (max-width: 640px)` で
`.video-viewport` を `aspect-ratio: auto; min-height: 60vh` にして
16:9 を捨てていた。幅 360px だと 16:9 の高さが約 200px しかなく、
`clamp()` の下限（`1rem` など）が効いて中身が溢れるためだった。

利用者と相談し、**16:9 を保ったまま画面幅いっぱいに縮める**方針に決めた
（文字が小さくなるのは承知の上）。

## やったこと

`claude_memo.html` と `CLAUDE.md` だけを変えた。

### 縮小の仕組み

スライドの中身（`slideData[].render()`）を書き直さずに済ませるため、
**プレイヤー全体を縮小表示**する形にした。

- `#viewport-stage` → `#viewport-frame` → `#player-viewport` の 3 段にした
- 768px 未満では `#player-viewport` を 960x540 のまま置き、
  `transform: scale(var(--vp-scale))` で縮める。`cqw` も `clamp()` も
  常に 960px 基準で解決されるので、スライド本文は PC と同じ組み方のまま小さくなる
- `--vp-scale` は `setupViewportScale()` が `ResizeObserver` で入れる
- 境界は Tailwind の `md:` に合わせて `767.98px`。当初は 640px だったが、
  641〜767px に元のはみ出し（スライド 4 / 13 / 17）が残るのでレビューを受けて上げた

### 字幕バナー

枠の中に置いたままだと 0.37 倍されて実効 5.2px になり読めないので、
`#subtitle-banner` を `#viewport-stage` の直下（枠の外）へ移した。
PC では絶対配置で枠に重ね、768px 未満では枠の下に流す。
`margin: 1px` は `#player-viewport` の 1px ボーダーを打ち消す値。

### 擬似フルスクリーン

- レターボックスを `#viewport-stage` 自身に持たせ、中身も字幕もそこを基準にした。
  当初あった `min()` による `100vh` 基準の計算は削除（アドレスバーが伸縮する
  実機でずれる恐れがあった）
- `:has()` をやめ、`setFullscreen()` が `is-fullscreen` / `pseudo-fullscreen` /
  `fs-lock` を 1 か所で付け外しする形にした（`:has()` 非対応の環境で
  フルスクリーンが完全に無反応になるため）
- 暗幕は `::before` の実体のある要素。`box-shadow` で描いていたときは
  タップが裏のヘッダーやフッターに素通ししていた
- 暗幕のタップでフルスクリーンを閉じる（スマホはボタンが覆われ Esc も押せないため）
- `body.fs-lock` は 768px 未満限定。PC で裏をスクロール禁止にすると
  スクロールバーが消え、`100vw` 基準の箱が横にずれる

### スライド切替でページがスクロールする件

実機（Android Chrome）で見つかった。`updatePlaylistSelection()` の
`item.scrollIntoView()` がスクロールできる祖先を全部動かすため、
チャプター一覧が画面の外にあるスマホ縦画面ではページごと動いていた。
`scrollPlaylistIntoView()` を足し、`#playlist-items` の中だけを
`getBoundingClientRect()` の差で計算してスクロールさせる。

## 確かめたこと

Chromium（`~/.cache/ms-playwright/chromium-1234`、`playwright-core`、`file://`）で実測。
このリポジトリにビルドもテストも無いので、すべてブラウザでの実測。

- 幅 360 / 390 / 430 / 641 / 700 / 767 / 768 / 844 / 932 / 1280 / 1440px の
  全 17 スライドで、枠からのはみ出し 0 件。コンソールエラーも 0 件
- PC（1280 / 1440 / 1920px）は HEAD と主要 7 要素の矩形が小数点以下まで一致。
  **スクロールバーを表示した状態**でもフルスクリーンの出入りで横にずれない
- スマホ縦のフルスクリーンで、字幕が枠の 12px 下に出てスライドと重ならない。
  暗幕のタップで閉じ、スライドや字幕のタップでは閉じない。Esc でも閉じる
- ページを `scrollY = 200` まで下げた状態から 17 枚を前送り・後戻りしても
  `window.scrollY` が動かない。`#playlist-items` に `position: relative` を
  付けても項目が枠の外へ出ない

実機での確認は利用者にお願いし、縦画面の表示は狙いどおりだった。

## 分担の振り返り

**各担当が何を見つけたか。**

- **reviewer が最も効いた。** 1 巡目で「字幕が実効 5.2px で読めない」
  「暗幕がタップを素通しする」を実測付きで挙げ、2 巡目で
  「PC で `fs-lock` がスクロールバーを消して横にずれる」
  「字幕が `100vh` 基準で実機ではずれる」、3 巡目で
  「`CLAUDE.md` の `md:` の説明が逆」を見つけた。どれも
  **「はみ出しが 0 件」では捕まらない**種類の問題で、
  verifier の確認だけで済ませていたら全部残っていた
- **verifier は「はみ出し 0」「矩形一致」を毎回きちんと出した**が、
  自分で確認の観点を増やすことはしなかった。3 巡目では報告を書かないまま
  3 回停止したため main が並行して実測し、そのあと verifier からも
  報告が届いた（結論は一致）。main の書いた報告ファイルは
  verifier に上書きされた
- **implementer は実装の質は高かった**が、自分の検証条件（ヘッドレス既定の
  `--hide-scrollbars`）の偏りに気付かず「PC は HEAD と矩形一致」と報告した。
  reviewer がスクロールバーを出して測り直して覆した

**見込みと食い違ったのはなぜか。**

見込みでは 1 巡で終わる想定だったが、**3 巡かかった**（$24.1）。
原因は、最初の依頼に「PC の見た目を変えない」としか書かず、
**「スマホで読める大きさを保つ」という条件を書かなかった**こと。
縮小方式は枠の中身を一様に縮めるので、字幕や枠上部のクロームが
読めなくなるのは方式の帰結だった。方式を決めた時点で予見できた。

**次に同じ規模の項目をやるなら。**

- **依頼文に「変えてはいけないもの」だけでなく「保たなければならないもの」を
  書く。** 今回なら「字幕は読める大きさを保つ」。これがあれば 1 巡減った
- **reviewer は最初から入れる。** 挙動が変わる項目で、
  「動くか」と「良いか」が別だという前提どおりの結果になった。
  料金の 26% を使ったが、見つけたものの重さに見合う
- **verifier に確認の観点を任せない。** 何を測るかは依頼側が決め、
  測る条件（スクロールバーの有無など）と**タイムアウトの目安**まで指定する
  （目安を書かないと待ち時間を見誤る。3 巡目で実際に詰まった）。
  今回 verifier が 8% しか使っていないのは、それだけ機械的な作業に
  収まっていたということで、そこは正しい使い方だった
- **実機でしか出ない不具合がある。** スクロールの件は 11 サイズの
  エミュレーションを全部通しても出ず、利用者の実機で初めて出た。
  スマホ向けの項目は、エミュレーションで固めたあと**必ず実機を挟む**
