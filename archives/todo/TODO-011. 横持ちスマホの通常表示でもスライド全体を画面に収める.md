## きっかけ

`setupViewportScale()` が外枠の**幅だけ**から `--vp-scale` を出していた。
横持ちのスマホ（844x390）では幅いっぱいに広げると 16:9 の高さが約 448px に
なり、画面の高さ 390px に収まらない。フルスクリーン中はレターボックスが
高さも見ているので収まるが、通常表示ではスライドの下側が画面の外に出ていた
（実測で 147px はみ出し）。

高さの基準は、利用者と相談して**画面の高さからヘッダーと本文の上余白を
引いた分**に決めた。操作列（再生・送りのボタン）は引かない。引くと
844x390 でスライドが 450x253 まで小さくなるため、操作列は少しスクロール
すれば出る形で妥協した。

## やったこと

`claude_memo.html` の `setupViewportScale()` に、枠の高さの上限を足した。

- 画面の高さから**枠の上端の実測値**を引いた分を高さの上限とし、
  `frame.style.maxWidth` に `上限 * 16 / 9` を入れる。幅の方が絞られ、
  `aspect-ratio: 16 / 9` が高さを決める
- `--vp-scale` は従来どおり枠の実寸から出すので、縮小率は自動で追随する
- `max-width` はインラインで入るためメディアクエリの外にも効いてしまう。
  CSS と同じ条件（`screen and (max-width: 767.98px), screen and (pointer: coarse)`）を
  `matchMedia` で見て、PC では空にする
- フルスクリーン中は枠自体がレターボックスで既に画面に収まっているので、
  上限を掛けない（掛けると二重に縮み、844x390 で 693x390 が 535x301 になる）。
  フルスクリーンの出入りは `#viewport-stage` の class を `MutationObserver` で見る
- `update()` は `ResizeObserver`（枠の幅）・`window resize`・`MutationObserver`
  （フルスクリーン）で走る
- 位置は `getBoundingClientRect().top + window.scrollY` で出す。
  ビューポート基準のままだとスクロール量の分だけ上限が伸びてしまう
- CSS 側に残したのは `margin-inline: auto` だけ（上限で幅が縮んだときの中央寄せ）

はじめは CSS だけで `max-width: calc((100dvh - 89px) * (16 / 9))` と書いたが、
89px（ヘッダー 65px + 上余白 24px）は幅で変わる値だった。ヘッダーは
`py-2 sm:py-3` で 640px を境に高さが変わり、バッジが折り返す 640〜712px の
帯では 89〜105px まで伸びる。iPhone SE の横持ち（667x375）で 16px はみ出す
ことが reviewer の実測で分かり、JS での実測に切り替えた。

## 確かめたこと

playwright（headless chromium）で実測。数値は
`archives/agents/TODO-011/verifier-report-2.md` と
`archives/agents/TODO-011/reviewer-report.md` にある。

- タッチ画面の通常表示 844x390 / 667x375 / 640x420 / 700x420 / 720x420 /
  767x420 で、枠の下端が画面の高さ以下（はみ出し 0）
- フルスクリーン（横持ち・縦持ち）は変更前と同じ大きさ。844x390 で 693x390
- 縦持ち 390x844 の通常表示、非タッチの PC 1280x800 は変更前と一致
- `--vp-scale` が枠の幅 / 960 と一致。複数スライドで本文が枠からはみ出さない
- スクロールした状態、回転相当（844x390 ↔ 390x844）でも枠の大きさが変わらない
- `ResizeObserver` が無い環境では上限が入らないだけで、変更前と同じ見え方。
  コンソールエラーは 0 件
- 利用者が実機（横持ち）で確認し、問題なしとの判断

## 分担の振り返り

- **reviewer が見つけたもの**: 89px という定数が幅で変わるヘッダーの高さに
  依存していること。640〜767px の帯を自分で測り直し、iPhone SE 横持ち
  667x375 で 16px はみ出すことを数値で示した。これが今回の作りを決めた
- **verifier が見つけたもの**: 1 巡目・2 巡目とも「通った」の報告のみ。
  ただし依頼で条件（画面サイズ、スクロール、回転、`ResizeObserver` 無し）を
  指定したのはこちらなので、指定しなかった穴は出てこない
- **main が見つけたもの**: フルスクリーンで二重に縮む回帰（実装直後の自分の
  実測）と、スクロール中に上限が伸びる問題
- **見込みとの差**: 担当の顔ぶれは見込みどおり。ただし 2 巡した。
  1 巡目で CSS の定数を選んだのは main の判断で、そこで「ヘッダーの高さは
  幅で変わる」に気付けなかった分がそのまま 1 巡になった
- **次に同じ規模ならどう組むか**: レイアウトの項目では、**測る画面サイズの
  一覧を項目を立てるときに決めておく**。今回 640〜767px の帯が抜けたのは、
  依頼を書く側が 844x390 だけを見ていたため。verifier の依頼に「代表的な
  実機サイズを 5 つ以上」と書いておけば、reviewer を待たずに 1 巡目で
  捕まえられた。reviewer に料金の 26% を使ったが、見つけたものの価値は
  それに見合っている（この項目の正否を決めた）ので、次も入れる
