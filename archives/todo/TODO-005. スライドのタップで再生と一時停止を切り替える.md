## きっかけ

フルスクリーン中のスマホでは、再生ボタンが暗幕の裏に入って押せない。
物理キーボードも無いので Space も使えず、タップで効くのは暗幕
（フルスクリーンを抜ける。TODO-003）だけだった。

## やったこと

`claude_memo.html` の 3 か所。

1. `#player-viewport` の click で再生と一時停止を切り替える。
   **通常表示でも効かせる**（動画プレイヤーと同じ振る舞いで、条件分岐が要らない）
2. 切り替えたとき、枠の中央に ▶ / ‖ を 0.5 秒ほど出して消す
   （`#tap-feedback-icon` と `@keyframes tapFeedback`）。
   大きさは `clamp(28px, 9cqw, 96px)`。768px 未満では枠ごと
   `--vp-scale` で縮むので、`px` 直書きにしない（TODO-001）
3. アイコンの絵柄は**切り替えた後の状態**を出す（再生を始めたら ▶）。
   動画プレイヤーの慣習に合わせた

**切り替えそのものは `playBtn.click()` に投げている。** 枠のタップが
そのセッションで最初の操作になることがあり、再生ボタン側の
`unlockFallbackAudio()`（無音を鳴らして Android Chrome の自動再生ブロックを
解く。TODO-002）とダミー発話を通す必要があるため。ユーザー操作の中から
同期で呼ぶので、解錠はそのまま効く。`speechSynthesis.resume()` を
3 か所目に書き写さずに済む利点もある。

暗幕のハンドラは `#viewport-stage` 自身の click で `e.target === stage` の
ときだけ反応するので、枠のクリックがバブリングしても当たらない。

## 確かめたこと

- **headless chromium 152 での実測** — 枠のクリックで `isPlaying` が交互に
  切り替わり、`#tap-feedback-icon` が ▶ / ‖ で `is-shown` になること。
  フルスクリーンに入ってから**初めて**枠をタップした経路でも
  `fallbackAudioElement` が作られる（＝解錠を通る）こと。
  そのあとも暗幕のクリックでフルスクリーンを抜けられること
- **verifier による確認** — 差分が 3 か所だけであること、既存の
  タップ操作・枠の外のコントロールと干渉しないこと、
  `pointer-events-none` の div が枠のクリックを塞いでいないこと。
  報告は `archives/agents/TODO-005/verifier-report.md`
- **reviewer によるレビュー** — 要修正 0 件。指摘した「解錠を通らない経路」を
  受けて `playBtn.click()` に委ねる形へ直した。報告は
  `archives/agents/TODO-005/reviewer-report.md`
**実機での目視確認はしていない。** headless chromium は PC の Chrome なので、
Android Chrome の自動再生ブロック（TODO-002）が実際に解けているかは、
コードの経路を追って確認しただけになる。横持ちのスマホで、
フルスクリーンに入ってから最初のタップで読み上げが鳴るかは、
気付いたときに確かめること。

## 残ること

**実機での目視確認（横持ちのスマホでのタップと読み上げ）が未実施。**
決着させた時点で利用者の返事を待っていたが、項目としては閉じた。

スライドの中に押せるものを置いたら、そのクリックは枠のクリックとしても
拾われ、再生と一時停止が同時に切り替わる。そのときは新しい要素側で
`e.stopPropagation()` を足すか、click の対象を絞る（reviewer の指摘）。

## 分担の振り返り

- **reviewer が本命の指摘を出した。** 「`play-btn` を一度も押さずに
  フルスクリーンへ入り、枠タップで初めて再生を始めると解錠を通らない」は、
  動作だけ見ていては出てこない（PC の chromium では再現しない）。
  verifier は差分の範囲と干渉の有無を実測で確認したが、この経路には
  気付いていない。**「動くか」と「良いか」を分けた効果が、そのまま出た例**
- 見込み（verifier + reviewer）との食い違いは無し。挙動が変わる項目に
  reviewer を入れる判断は当たった
- **次に同じ規模（1 ファイル・ハンドラ 1 つの追加）をやるなら、同じ編成で
  よい。ただし reviewer を先に、verifier を後に回す。** 今回は並行で
  走らせたため、reviewer の指摘で実装が変わり、verifier の実測は
  古い差分に対するものになった（結論は変わらなかったが、測り直しは main が
  やった）。逐次にすれば verifier の分を 1 回で済ませられる
